## 指導原則（老闆要求，全份報告都跟呢條）

> **「每個月重複嘅嘢就系統全部幫手做，唔好要人手每月重複做。」**

- 每個月要人做一次或以上嘅步驟，**一律當高優先自動化候選**，唔會因為「每次得幾下掣」就當細事。
- 每個月度步驟都會講清楚三樣嘢：系統**已經有晒**邊啲資料、**仲差**乜，同埋建議用邊種形態處理：
  - **(a) 全自動跑，跑完通知**：首選。
  - **(b) 系統預備好，人一撳確認**。
  - **(c) 暫時仍然要人做，但 AI 預填同解釋**。
- 盡量推向 (a)。唔揀 (a) 嘅項目會寫明原因（例如涉及錢要人簽、規則未定、冇資料）。

## 方法

- 讀咗：`src/app/(app)/**` 頁面 code（數掣、表單、對話框、覆核步驟）、`src/app/api/**`、`src/lib/**`（重點：`month-close/one-click.ts`、`month-close/auto/*`、`triage/*`、`roster-upload/*`、`longterm-payroll/*`、`ai/**`）、`src/components/ai/**`、`tests/e2e/*.spec.ts`（當「逐步操作紀錄」用嚟數步數）、`README.md`、`docs/api.md`、`docs/ai-assistant.md`、`prisma/schema.prisma`、migrations。
- **冇讀**（獨立性規則）：P0–P3 計劃文件、`docs/perf-2026-10/`、設計文件、git log、commit message。
- 冇碰共用 DB、`.env`、`data/`。我試過喺 scratchpad 複製一份做 `next build`，但因為 repo 嘅 Prisma client 未 generate，喺 type check 失敗。我冇喺共用 `node_modules` 重新 generate，所以今次**冇** bundle 數字，亦冇做實機量度。

## 限制（老實講）

- **「每月幾多次」同「每月慳幾多分鐘」全部係由 code 同 e2e 推估，唔係真實使用量**。系統冇使用量統計，我亦冇睇真實資料。下面用咗**假設規模**：每月約 20 個盤、約 30 條待答題、約 40 位長工、約 5 個雞頭。真實數字唔同，比例照計。
- 「每步大約幾耐」用一般後台操作估：撳一下掣約 5 秒；揀檔上載約 30 秒；覆核一題約 30–60 秒。
- 有幾處要老闆或會計確認業務規則先自動得（例如勤工獎點計、介紹費例外），下面會標「規則未定」。
- 有一項我搵唔到 UI 入口：「開新月」（`POST /api/months/:month/open`）喺頁面 code 冇人 call，只喺 e2e／API 文件出現。所以我推斷而家係靠其他方式做或者冇人做（**疑似**，要人手確認）。

## 一、現有流程人手步驟盤點

先講結論：**「一鍵結算」已經將月結中段（建盤、補更種、保安員修復、對數套用、自動定價、介紹費重算、長工糧重算、出報告）自動晒**（`src/lib/month-close/one-click.ts`，10 步）。人手主要卡喺四個位：
1. **月頭準備**：開月、複製上月嘢。
2. **每月搬檔入系統**：上載更表、U Team 名單、Postorder、Maxwell、Payroll Editor。
3. **答題**：一題一題答。
4. **月尾簽收同匯出**：鎖月、下載糧單、autopay、總表。

而且**系統完全冇排程（cron）同對外通知渠道**（搵唔到任何 email／WhatsApp／web push／cron）。所以每樣嘢都要人開 App 撳。首頁有「待辦收件箱」（`src/app/(app)/page.tsx`），但只喺開 App 嗰陣先見到。

## 二、「在勤助手」擴展場景

**而家助手做到乜**（`src/lib/ai/tools/index.ts`、`actions.ts`、`components/ai/ActionCards.tsx`）：
- **21 個唯讀工具**：盤、更表、雞頭統計、價卡、保安員查詢、毛利、月結、尚欠、操作紀錄、SQL 查詢、一鍵結算狀態、待答題摘要、鎖月前體檢、每月修正摘要、盤設定、定價解釋、錯誤紀錄。
- **6 種動作卡**：開頁、答一題、設盤預設雞頭、重新解析上載、跑一鍵結算、補齊價卡。
- 每張卡都要人撳，之後有 5 秒撤銷，再經**同人手一模一樣**嘅 API 送出。鎖咗嘅月會過濾走寫入卡。
- 助手架構上冇任何寫入工具，呢個安全底線好，建議保持。

下面每個場景都沿用同一個模式：**AI 只提議同解釋；寫入一律經現有 API 同現有權限；人撳確認；可以撤銷**。

| 場景 | AI 讀咩（唯讀） | AI 提議乜 | 人喺邊度確認 | 錯咗會點、點撤銷 | 要新增嘅工具／卡 |
|---|---|---|---|---|---|
| S1 待答題批量清 | `triage_summary`、每題 evidence（已經遮咗身份資料） | 「呢 18 題係高把握建議，建議全部接受；呢 4 題要你揀；呢 2 題我建議跳過」，每題一句理由 | 一張「批量接受（N 題）」卡，展開睇清單，一撳 | 每題都有現成撤銷（`undo-backfill`、`undo-auto`）；批量卡應該逐題記 preview_hash，撤銷都係逐題 | 新卡 `triage_accept_batch{question_ids[]}`；server 逐題 preview 再 answer |
| S2 未定價或新盤冇價 | `pricing_explain`、`rate_cards`、上月同盤同更種價、相近盤價 | 「建議用上月 $X（依據：同盤同更種上月卡）」或者「相近盤中位數 $Y」 | 現成 `triage_answer`（mc_pick／mc_price） | 價錯就影響收入或成本；鎖月前可以改；卡要顯示金額同依據 | 加工具 `price_candidates`（上月、相近盤、Postorder） |
| S3 未配對保安員 | 更表行（遮咗身份資料）、候選 guard id、同盤歷史出更、工號相似度 | 「呢行最似保安員 #id，同盤上月出咗 12 更、工號尾 4 位一樣」 | `triage_answer`（link）；新人就開頁去證件建檔，連預填 | 配錯人等於糧出錯人：**一定要人確認**，唔可以全自動。撤銷靠改配對再重新對數 | 加工具 `guard_match_candidates`（只出 id 同分數，唔出真名） |
| S4 對數差異（以更表為準定以系統為準） | 對數結果分類、更數差異（variance） | 逐盤一句：「呢盤 14 格系統冇、更表有，全部係同一雞頭補更，建議以更表為準」 | 新卡 `reconcile_apply_roster{upload_id, category}`，即係對數頁「全部以更表為準」同一個 API | 鎖月前可以再改；對數決定會留紀錄 | 新卡一種 |
| S5 鎖月前體檢 | `month_health`、`one_click_status` | 用人話講「仲差 3 樣先鎖得：…」，每樣附開頁卡；全部清咗就話「可以鎖」 | **鎖月本身唔做成 AI 卡**：牽涉錢，要老闆親手撳。卡只帶去鎖月區 | 鎖月由人做，冇新風險 | 唔使新卡；system prompt 加一個「鎖月前清單」範本 |
| S6 長工糧人手輸入 | 長工 leave 更（SL/AL/NL）、頂位更、上月輸入 | 「X 號長工本月更表有 SL 2 日，建議開一段病假（醫生紙待核）」「上月有制服扣款 $N，今月照抄？」 | 新卡 `longterm_input_draft{guard_id, kind, …}`，一撳寫入，之後撳重算 | 錯咗影響出糧金額：**一定要人覆核**；輸入有作廢功能，可以撤銷 | 加工具 `longterm_input_suggestions`、新卡一種 |
| S7 新保安員建檔 | OCR 結果、導入包分診題 | 「呢份證件同現有 #id 好似係同一人（出生日期同電話尾數一樣），建議連結，唔好新開」 | 現成分診題答案 | 身份資料敏感：AI 唔見原文，只見遮罩後特徵 | 唔使新卡，加解釋 prompt |
| S8 每月修正摘要變「下個月點樣唔使再改」 | `ops_digest` | 「上月有 9 次手動改同一盤嘅結算雞頭，建議設定盤預設雞頭」 | 現成 `site_set_default_broker` 卡 | 低 | 唔使 |
| S9 雞頭審批 | 待審更、配額、掛盤、重疊更 | 「32 條全部喺配額內、冇重疊，建議全批；2 條超配額要你睇」 | 新卡 `approve_batch{ids[]}` | 批錯可以作廢 | 新卡一種（最好配埋 server 端批量 API，見技術部分） |

**一個要留意嘅部署前提**（`docs/ai-assistant.md`）：正式站喺香港節點打 Anthropic API 會被地區封鎖，要搬新加坡或者用 DeepSeek。AI 場景喺部署層面未必即刻用得到。

## 三、適合交俾系統自動跑嘅重複工作（唔使開 App）

**要先補嘅基建（全部都要靠呢兩樣）：**
- **排程器**：Zeabur cron，或者外部 pinger 定時打一個帶密鑰嘅內部 endpoint。
- **通知渠道**：而家只有首頁收件箱。建議加一張 `notifications` 表，加推送渠道（WhatsApp Business API 或者 email；最平嘅起步係 email）。
- 工作量估：**M（1–3 日）**。

| # | 自動工作 | 幾時觸發 | 輸入 | 輸出去邊 | 風險 | 要人確認？ |
|---|---|---|---|---|---|---|
| J1 | 自動開新月（複製掛盤、配額、每日需求、上月價卡） | 每月 25 號，或者上月鎖定嗰刻 | 上月資料 | 收件箱：「8 月已開好：掛盤 N、配額 N、價卡 N（候選 M 張要你睇）」 | 低。API 唔會重複寫；價卡可以作廢 | 價卡金額變咗嘅先要確認 (b)；其餘 (a) |
| J2 | 每晚體檢（`month_health`） | 每晚 | 本月資料 | 有新紅項先推送 | 低（唯讀） | 唔使 |

## 四、月度重複操作總表（要齊全；每月步數係推估）

| 操作 | 角色 | 而家每月幾多步 | 建議形態 | 自動化後每月幾多步 | 已經有／仲差 | 前提／風險 |
|---|---|---|---|---|---|---|
| 開新月（掛盤、配額、每日需求） | 主管 | 1 次 API；**UI 搵唔到入口**（疑似靠逐條人手開） | **a** | 0 | 有：API 識複製、唔會重複寫；差：排程、UI 入口 | 雞頭或盤有變就要改，可以改完先 |
| 複製上月價目卡 | 老闆／會計 | 3 步（撳 → 睇預覽 → 確認），可能按盤重複 | **b**（價錢有變先要確認） | 0–1 | 有：copy-last-month API、候選；差：排程 | 加價月份要人改價 |

## 總評

系統喺月結中段已經做到相當高嘅自動化，安全底線亦大致穩陣（全部 API 都經權限檢查、DTO 白名單、AI 唯讀）。最大嘅空間係兩頭：**月頭準備**同**月尾簽收或匯出**仍然靠人逐樣撳，而且**系統冇排程、冇通知**，所以任何「自動」都要人開 App 先發生。補返排程同通知、加一個「批量接受建議」掣，已經可以做到「每月重複嘅嘢系統做」嘅大部分。技術方面，要先補 H1–H4 幾個鎖月漏洞，否則越自動化（例如檔案自動入、上載後自動跑），已鎖月份被改嘅機會反而越大。
